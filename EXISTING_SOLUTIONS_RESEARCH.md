Global LUTs apply the same mapping to the same input color at every position. They can improve global tone/palette but do not independently understand a sky, face or rock. Regional control needs a bilateral grid, mask or other spatial conditioning; add it only after a concrete failure persists. Direct diffusion retouching is a later comparison because content fidelity and local runtime need separate checks; InstantRetouch's [paper](https://arxiv.org/abs/2606.05071) explicitly motivates bilateral transforms by multi-step editor cost/content drift. No published GPU milliseconds are treated as measurements on our Mac.

For our first comparison, each frozen model should start from the correctly decoded sRGB source or the neutral camera-WB RAW development, independently of the current adjusted candidate. Do not stack an unvalidated learned look on Lift shadows or another learned output. Keep original/current-native/model results together; verify full-resolution export, native sky/skin/rock details, identity at0%, ordinary/daylight/night negatives, time/memory and exact PNG metadata. Existing FiveK diagnostic photos may overlap external training; use separate personal-camera sources for later preference acceptance. The frozen10-case fine-tuning set is reusable regression evidence, not a fresh held-out quality set.

After a model provides consistently preferred results, record user-accepted edits/choices. A small predictor of our actual native recipe/relative controls is the simplest controllable personalization route, with new renderer-specific supervision. A fixed expert style or user target images can supervise a separate image-to-image/LUT retouch task after color/alignment/group auditing; do not average expert styles into an assumed unique photographic truth, proxy-fit new values and relabel them as official Catalog labels, or train before suitable targets exist. This extends the earlier mature-backend-first decision without promoting any automatic model now.

### Engine feasibility and exact local constraints

**RawTherapee.** Its CLI accepts a processing profile with `-p`, handles RAW/non-RAW defaults, and exports PNG/TIFF/JPEG. PP3 profiles can be layered. Auto Levels is explicitly described as a starting point for typical photographs rather than a universal aesthetic decision. Existing denoising distinguishes chrominance from luminance and offers conservative/detail controls. These capabilities support a bounded natural-adjustment baseline without another training project. [CLI](https://rawpedia.pixls.us/command-line_options/), [Auto Levels](https://rawpedia.pixls.us/exposure/), [denoising](https://rawpedia.pixls.us/noise_reduction/).

The actual host reports **macOS 14.8.4, arm64**. Neither CLI was found on PATH. Official RawTherapee 5.13 requires macOS 26 on Apple Silicon; 5.12 requires 15.4. The official universal 5.11 package requires 12.3 or later, making it the initial compatibility candidate. This is an OS-requirement check, not a successful installation/run. Use 5.11 documentation/source and a profile saved by that version when implementing; current documentation may describe newer tools. [5.13 requirements](https://www.rawtherapee.com/downloads/5.13/), [5.12 requirements](https://www.rawtherapee.com/downloads/5.12/), [5.11 requirements](https://www.rawtherapee.com/downloads/5.11/).

Proposed call shape, after installing/verifying the engine and creating an actual reviewed profile:

```sh
rawtherapee-cli -o /tmp/adjusted.png -p /path/to/natural.pp3 -n -b8 -c /path/to/source.jpg
```

The profile is a planned artifact, not an existing file. Run with isolated settings, explicit sRGB output, independent output paths and a versioned profile; do not inherit the user's personal GUI defaults or sidecars. A neutral engine render is not necessarily byte-identical to the decoded JPEG. Implement strength zero as an explicit bypass returning the existing decoded source, rather than assuming a neutral PP3 is identity.

**darktable.** The current install page offers ARM64 macOS packages supporting macOS 13.5 onward. Its console exporter accepts XMP/history, output dimensions and color-profile settings. Tone equalizer uses a guided luminance mask to apply different exposure adjustments to different tonal regions while retaining local contrast. It is a meaningful alternative when the current global renderer fails on a dark subject against a bright background. Masks still need tuning and can create halos; brightness regions are not semantic subject masks. Freeze engine/module/profile versions and isolate its configuration/library. [Installation](https://www.darktable.org/install/), [CLI](https://docs.darktable.org/usermanual/5.6/en/special-topics/program-invocation/darktable-cli/), [tone equalizer](https://docs.darktable.org/usermanual/5.6/en/module-reference/processing-modules/tone-equalizer/).

Adobe Lightroom CC is present locally, but this does not establish Lightroom Classic availability, a usable license/session, headless batch support or faithful legacy Catalog export. Do not make completion depend on an assumed Adobe automation path.

### Neural options: what the source actually supports

**Image-adaptive 3D LUT is the first neural comparison.** The author provides pretrained sRGB/XYZ variants and a source-image demo. A small predictor mixes basis LUTs; the resulting transform can be applied at original resolution. Prefer the sRGB variant for our color-managed JPEG path. The old implementation relies on custom trilinear interpolation; the author links a native `grid_sample` replacement discussion. A minimal adapter should keep the frozen predictor/LUTs, explicitly validate channel/axis order, endpoints and interpolation parity, and process high-resolution pixels in bounded chunks. Do not import the complete old training stack. Neither native MPS/ONNX operation nor current-host speed is established. The author's demo runs without a reference image; this does not establish generalization to our camera or guarantee natural output. [Author repository](https://github.com/HuiZeng/Image-Adaptive-3DLUT), [demo source](https://github.com/HuiZeng/Image-Adaptive-3DLUT/blob/master/demo_eval.py).

**NeurOp is the next comparison if user control matters.** The author repository supplies Paddle/PyTorch implementations and pretrained FiveK/PPR10K models. The paper models editing as a sequence of color operators with scalar strengths. The PyTorch `test.py` is a paired scoring harness that accesses GT; isolate the image-only forward path rather than copying the harness into the app. Verify input variant, full-resolution behavior, weights and operator identities before use. FiveK-Dark/Lite are different rendered-input protocols, and neither matches arbitrary phone JPEGs automatically. [Paper](https://arxiv.org/abs/2207.08080), [repository](https://github.com/amberwangyili/neurop), [test source](https://github.com/amberwangyili/neurop/blob/main/codes_pytorch/test.py).

**DeepLPF is not the immediate integration choice.** The current author repository offers checkpoints and a CPU/CUDA/MPS CLI, but its package requires Python >=3.11 and NumPy >=2.0; ShotSense is pinned to Python 3.9.8/NumPy 1.26.4. More importantly, `model.py` identifies the first backbone channels as an enhanced image and applies learned filters to that image. Interpretable filters do not mean all output pixels are merely original pixels multiplied by safe gains. If tested later, use an isolated environment and an explicit checkpoint/split; the current repository's reconstructed and DPE checkpoints are distinct. Its simple image loader also needs our EXIF/ICC decoder. Published/README timing is not a measurement on this host. [Repository](https://github.com/sjmoran/deeplpf-image-enhancement), [package requirements](https://github.com/sjmoran/deeplpf-image-enhancement/blob/master/pyproject.toml), [network source](https://github.com/sjmoran/deeplpf-image-enhancement/blob/master/model.py), [CLI decoder](https://github.com/sjmoran/deeplpf-image-enhancement/blob/master/deeplpf_cli.py).

**Apple Core Image** exposes automatically selected/configured adjustment filters. This is a native Mac-only comparison, not the recommended cross-platform backend or proof of Photos' Auto equivalence. [Apple API](https://developer.apple.com/documentation/coreimage/ciimage/autoadjustmentfilters%28%29?language=objc).

### Smallest route to a complete useful version

1. **Establish one real photographic baseline.** Keep the existing Streamlit worker, decoder, before/after comparison and exports. Compare original/current renderer/RawTherapee on a fixed development set. Start with three recipes: unchanged, conservative natural tone, and conservative tone with denoising. Freeze or disable white-balance, saturation, sharpening and detail reconstruction unless their own review supports them. Compare darktable only if the first engine cannot handle the fixed backlight/local-tone cases.
2. **Make automatic choices bounded and reviewable.** First use source statistics and a few fixed rules to propose one recipe; allow original/no change as an outcome. Evaluate dark intentionally lit/night scenes separately from accidentally underexposed photos. Render alternative previews for user correction, but use one proposed result as the default. Diagnostics can reject bad candidates; histogram or color thresholds are not calibrated confidence or proof of good taste. Do not add a learned router, segmentation model or general framework before the simple version's failures justify one.
3. **Compare one frozen neural retoucher.** Run the sRGB adaptive-LUT model on the same decoded images. It must beat the engine on preference/detail/color review to justify integration. Stop this comparison if it does not; NeurOp is a conditional next candidate, not another model to install immediately. Keep specialized restoration an explicit separate mode.
4. **Close the export loop.** Analyze a small preview, apply the same recipe to original-resolution pixels, then derive the displayed final preview from that export. Cache a low-resolution source for interaction, but preserve the full-resolution source for export. Measure actual latency/memory before retaining or changing the 60-second/40MP limits. A 960/1600px preview download is not completion of a full-resolution editing tool.
5. **Train only after useful examples exist.** Collect user choices/edited examples. If a small selector is needed, learn preferences among the bounded recipes; if full retouching is needed, obtain compatible rendered input/target pairs for one chosen style. Labels for this new task are engine recipes or preferred images, explicitly separate from the six official Catalog fields. Do not manufacture or relabel Adobe parameter ground truth. Existing adaptive-LUT resources offer low-resolution FiveK pairs; audit their rendering and source IDs before reuse, and avoid downloading the full RAW dataset again. Existing FiveK/LOL data may overlap external checkpoints.

The RAW recommender remains separately versioned and optional during this path. Its old absolute Exposure/HighlightRecovery outputs do not directly configure the new engine. A future learned engine-control recommender requires fresh supervision/evaluation for that renderer.

## Decision from our experiments

Prioritize a frozen pretrained image-restoration comparison before another tiny custom model. Our local additive CNN improved fidelity but increased dark variation and produced gray shadows. The subsequent fixed-denoiser/illumination pilot reduced visible grain and its dark-variation proxy, but blurred foliage/buildings/text and worsened color. A stronger fixed filter or another brightness-only head is not supported by these results. These are observations from small development sets, not a controlled proof of the underlying cause. See [spatial pilot](artifacts/experiments/jpeg_spatial_v1/ACCEPTANCE.md) and [separate illumination pilot](artifacts/experiments/jpeg_illumination_v1/ACCEPTANCE.md).

Keep the DNG Catalog-parameter recommender and rendered-JPEG restoration task separate. A restored image is not evidence that six Lightroom parameters reproduce it. A JPG/JPEG input should enter the restoration model as its correctly decoded RGB image, following the selected model's contract; do not first apply our RAW-trained experimental parameter estimates. This prevents inherited erroneous brightening from becoming the fixed input to every candidate.

**HVI-CIDNet.** Its HVI representation and color/intensity branches target color instability and dark artifacts, making it a particularly relevant hypothesis for our casts. This relevance is an inference, not a prediction of local gains. The author repository provides trained variants and distinguishes reference-mean-corrected scores and test-finetuned weights. Use neither for unbiased deployment evaluation. The author lists a synthetic-LOLv2 random-gamma generalization variant, but the exact Hugging Face Generalization checkpoint's model card does not establish its complete training set. The official linked web demo currently returns a configuration error; local weights are a more suitable evaluation route. [Author repository](https://github.com/Fediory/HVI-CIDNet), [model card](https://huggingface.co/Fediory/HVI-CIDNet-Generalization), [demo status](https://huggingface.co/spaces/Fediory/HVI-CIDNet_Low-light-Image-Enhancement_).

The Generalization card lists roughly1.98M FP32 parameters and MIT metadata. Author code also uses MIT. Its app has a CPU option, whereas the HF evaluation script hardcodes CUDA, uses non-strict state loading, and exposes gamma/color/intensity gates. A local adapter must explicitly choose CPU, require complete state matching and freeze all inference settings rather than tuning each image to its target. Existing code does not establish MPS/ONNX compatibility or local latency. [Model card](https://huggingface.co/Fediory/HVI-CIDNet-Generalization), [license](https://github.com/Fediory/HVI-CIDNet/blob/master/LICENSE), [CPU app](https://github.com/Fediory/HVI-CIDNet/blob/master/app.py), [HF evaluation](https://github.com/Fediory/HVI-CIDNet/blob/master/eval_hf.py).

**Retinexformer.** Combines illumination estimation with restoration and illumination-guided attention to model broader image context. The author repository provides pretrained inference and high-resolution split/test support under MIT code licensing. Evaluate it as an independent recipe; published GPU/high-resolution results do not certify our Mac or tiled outputs. Its `GT_mean` mode explicitly uses the reference mean and must remain off. [ICCV paper](https://openaccess.thecvf.com/content/ICCV2023/papers/Cai_Retinexformer_One-stage_Retinex-based_Transformer_for_Low-light_Image_Enhancement_ICCV_2023_paper.pdf), [author code](https://github.com/caiyuanhao1998/Retinexformer), [license](https://github.com/caiyuanhao1998/Retinexformer/blob/master/LICENSE.txt).

**NAFNet.** Provides SIDD-trained denoising checkpoints and an image demo. It supplies a useful learned-denoiser control to distinguish restoration benefits from the strong nonlocal-means smoothing we observed. It is not itself a low-light brightness/color solution, and its benchmark performance cannot be transferred to dark phone JPEGs. The repository's main license is MIT, with separate bundled BasicSR terms; preserve attribution for reused code. CPU/MPS and noise-domain behavior require measurement. [Official repository](https://github.com/megvii-research/NAFNet), [license](https://github.com/megvii-research/NAFNet/blob/main/LICENSE).

**Regional and semantic research.** SNR-aware LLIE uses different spatial context according to noise conditions, offering a basis for replacing one-strength-everywhere denoising. HVI-CIDNet+ introduces pretrained vision-language priors for extreme-dark content/color restoration. These support investigating regional noise and semantic cues; they do not prove semantic labels should directly set exposure. Its linked + repository could not be retrieved during this review; do not confuse the accessible2025 base model with the + implementation. [SNR paper](https://openaccess.thecvf.com/content/CVPR2022/html/Xu_SNR-Aware_Low-Light_Image_Enhancement_CVPR_2022_paper.html), [author implementation](https://github.com/JIA-Lab-research/SNR-Aware-Low-Light-Enhance), [HVI-CIDNet+ preprint](https://arxiv.org/abs/2507.06814).

LightenDiffusion learns latent reflectance/illumination from unpaired data and provides author code/weights. It is a later research comparison rather than the first local dependency expansion; sampling cost, consistency and preservation of real detail need separate checks. [ECCV paper](https://www.ecva.net/papers/eccv_2024/papers_ECCV/html/6440_ECCV_2024_paper.php), [official code](https://github.com/JianghaiSCU/LightenDiffusion).

The2026 efficient-LLIE challenge report supports broader-context restoration, color separation and multiple perceptual/structure metrics under deployment constraints. Its results do not prove that the original Retinexformer checkpoint is the winning variant or that winner weights are ready for local use. Read it for later compression and evaluation design after establishing quality. [Primary challenge report](https://arxiv.org/html/2605.02212v1).

## Evaluation pitfalls and proposed bounded next step

LOLv1 pretrained checkpoints can have seen all our `our485` images during their own training. Our custom held-out grouping does not turn those into unseen images for an external model. Scores on them are regression/development diagnostics only. Checkpoint labels such as Generalization, normal or best are insufficient provenance. Freeze exact source revision, downloaded bytes/hash, configuration and known training datasets; mark unknown overlap explicitly.

First freeze HVI-CIDNet and Retinexformer inference configurations without training. Start with the original pet/indoor failures, foliage/text and an already-bright negative control for visual regression, then evaluate a separate small set of known-unseen personal/independently acquired scenes. No private photos should be uploaded to hosted demos automatically. Keep official test pixels protected until a final model/evaluation protocol is frozen; do not repeatedly use them to select methods.

Run identity, current website behavior, each complete pretrained restoration recipe and, if needed, a NAFNet-denoising control on the same decoded source images. Turn off reference-mean correction and exclude test-finetuned checkpoints. Fix any strength/gamma/color options before scoring; brightness-aligned diagnostics, if recorded, must be separate from source-only deliverable scores. Preserve dimensions/EXIF/ICC handling and identical export pixels.

Where references exist, measure per-image PSNR, SSIM, color error and detail preservation, while reviewing native crops for text/fur/foliage, halos, raised blacks, clipping, casts and blur. No-reference scores are supplementary; a lower noise proxy from smoothed texture is not acceptance. Include dim scenes, extreme dark, mixed lighting, daylight and intended silhouettes: enhancement must not force every dark photo toward daylight.

Measure actual CPU first, then optional CPU/MPS output parity before acceleration. Record end-to-end time, memory, resolution and padding/tiling seams. Protect the current environment with isolated adapters/environment if upstream dependency versions conflict. Do not copy entire training frameworks merely to run inference. Training or ONNX integration follows only after a visually convincing baseline, known-unseen evidence and runtime/export checks. Initial recommendation: establish these two complete pretrained baselines before another custom architecture or loss experiment.
